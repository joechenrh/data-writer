# 用户自定义 Go 列生成器 — 设计文档

**状态**：Draft v1 · **作者**：joechenrh · **日期**：2026-04-21

---

## 1. 背景

data-writer 现在按 SQL 列类型走内建 generator，通过 COMMENT 旋钮（`null_percent` / `max_length` / `mean` / `stddev` / `order` / `set` / `compress`）控制。这些旋钮覆盖"独立分布"场景，但覆盖不了需要自定义逻辑的列——前缀拼序号、同行派生、条件取值、哈希指纹、模板多字段等。目前这类列只能靠外部工具（perftest 的 Lua 脚本）实现，没法用 data-writer 的高吞吐批量写 parquet/CSV 管线。

本设计给出一个最小改动的方案：**用户能在 Web UI 里为指定列写 Go 函数，函数随任务通过 DB 一起带到 EC2，EC2 rebuild data-writer 二进制后执行**。

## 2. 目标 / 非目标

### 2.1 目标

- **G1** — 用户在现有 Web UI 里能对指定列写 Go 函数覆盖默认生成行为。
- **G2** — 任务执行性能不受影响：用户代码在 EC2 上编进 data-writer 二进制，调用开销为纳秒级。
- **G3** — 对没写 Go 代码的列完全向后兼容。
- **G4** — 失败都能在 UI 上看到原因（语法错误、编译错误、运行时 panic）。
- **G5** — dispatch server 侧**零 Go toolchain 依赖**；build 全部放在 EC2。

### 2.2 非目标

- **N1** — 受限 TOML DSL 层（如 `= uniform_int(...)` 表达式语法）。自用场景下用户直接写 Go 就行，加 DSL 只会让 spec 和解析器翻倍。
- **N2** — 拓扑排序 / 列依赖 DAG / 自动推断 deps。规则是"Go 函数只能读 SQL 里排在自己前面的列"，用户改 CREATE TABLE 列顺序比学拓扑规则成本低。
- **N3** — parquet 慢路径整-RG buffer 切换（原 perftest-oriented spec §8.2）。砍了拓扑后不再需要。
- **N4** — scaffold 幂等合并 / 本地 CLI `data-writer submit`。前端在浏览器里 Monaco 编辑，scaffold 是一次性生成文本。
- **N5** — 服务器侧 `go build` workspace、10 行样本预览 fork-exec。所有 build 在 EC2。
- **N6** — import 白名单 / 沙箱。自用信任边界内，让 EC2 的 `go build` 报错即可。
- **N7** — 跨行 / 跨表依赖。同 spec v0 延后。
- **N8** — `target=local` 模式下的用户代码支持。有 `generators_go` 的任务**只允许** `target=ec2`。

## 3. 总体流程

```
浏览器                              dispatch server                 EC2 worker (per-shard)
────────                            ────────────────                ──────────────────────
1. 粘 SQL，点"生成 Go 骨架"
   POST /api/scaffold {sql}  ──►   解析 SQL → 返回 Go 文件文本
                              ◄──  {generators_go: "package user\n..."}

2. Monaco 编辑器里改函数体

3. 填 path/rows/... ，点"提交"
   POST /api/create          ──►   go/parser parse-only 校验
   {sql, generators_go, ...}       通过 → INSERT INTO tasks
                                   (sql_text, config_json,
                                    generators_go, target='ec2', ...)
                              ◄──  {task_id: 123}

                                    (ec2-launcher cron 外部调度)
                                    ──► aws ec2 run-instances ...

4. (EC2 boot 完毕)                                                   ./launcher.sh
                                                                     ├─ claim-task 拿到 (tid, shard, total)
                                                                     ├─ dump-generators → user_gens.go
                                                                     ├─ 若非空：codegen + go build
                                                                     │    失败 → report-failure + shutdown
                                                                     ├─ data-writer -worker-mode ... → 写 S3
                                                                     └─ shutdown

5. UI 轮询 /api/status
                              ◄──  state=completed / failed + error
```

## 4. 数据模型变化

`tasks` 表加一列：

```sql
ALTER TABLE tasks ADD COLUMN generators_go TEXT;  -- nullable
```

- `NULL` / 空串 → 任务无自定义 Go 代码，走现有管线（零回归）。
- 非空 → **整个 `user_gens.go` 文件的文本内容**。EC2 worker 原样写盘。

**不新增**其他列、不新增表、不新增 `[columns]` / TOML 字段。信息的唯一事实源就是这段 Go 代码本身——函数名 = 覆盖哪列，函数体 = 做什么。

## 5. API 变化

### 5.1 `POST /api/scaffold`（新）

```json
// req
{"sql": "CREATE TABLE test.t (user_id BIGINT, device_finger VARCHAR(12));"}

// resp
{"generators_go": "<file text>"}
```

对 CREATE TABLE 每一列生成一段**注释掉的**函数。示例产物：

```go
// Code generated by data-writer scaffold. Edit freely.
// Task: test.t
//
// How to use:
//   - Uncomment a function to override that column's default generator.
//   - Function name is column name in PascalCase (user_id -> UserId).
//   - Read sibling columns with ctx.Int64("user_id"), ctx.String("..."), etc.
//     You can only read columns that appear earlier in CREATE TABLE than
//     the current one; reading a later column panics at runtime.
//   - Return value must match the column's Go type (see each stub's comment).
//   - Return nil for NULL.

package user

import "dataWriter/src/gen"

// Column: user_id  SQL: BIGINT  -> return int64 or nil
// func UserId(ctx *gen.Ctx) any {
//     return ctx.Rng.Int63n(5_000_000)
// }

// Column: device_finger  SQL: VARCHAR(12)  -> return string or nil
// func DeviceFinger(ctx *gen.Ctx) any {
//     return ""
// }
```

### 5.2 `POST /api/create`（扩展）

现有请求体加一个可选字段：

```json
{
  "sql": "...",
  "generators_go": "package user\n...",   // 新增，optional
  "path": "...", "rows": 10000, ...
}
```

处理逻辑：

1. 和现有一样做 SQL 解析和 config 校验。
2. **若 `generators_go` 非空**：
   - 强制 `target = "ec2"`，`target=local` → 400。
   - 跑 `go/parser` parse-only（不做 type check / 不 resolve 符号），失败 → 400 + parser error。
   - 通过 → 写进 `tasks.generators_go` 一起 INSERT。
3. 返回 `task_id`。

### 5.3 没有 `/api/preview`

`/api/preview` 被设计出来是为了"改完看 10 行样本"——但它需要在 dispatch server 侧 `go build` + fork-exec，与 §6 "dispatch 零 toolchain" 矛盾。本 spec **不包含** `/api/preview`。

要看输出，就提交一个小规模任务（`rows=100, folders=1`）到 EC2。EC2 冷启动 1–3 分钟是 dev loop 下限，在自用场景可接受。后续如果迭代成本高到值得优化，可单独引入"preview EC2 pool"或"本地 CLI" — **不在本 spec 范围**。

## 6. Go 模板与 `gen.Ctx` API

### 6.1 新增 `src/gen` 包

```go
package gen

import (
    "math/rand/v2"
    "time"
)

type Ctx struct {
    RowID int64
    Rng   *rand.Rand   // worker-local，seed 由调度层注入
    // 私有字段：当前行已生成列的类型化 buffer
}

// 读兄弟列（只允许读 CREATE TABLE 里排在当前列之前的列；
// 读后面的列或不存在的列 → panic，stderr 打印 row/col）
func (c *Ctx) Int32(col string) int32
func (c *Ctx) Int64(col string) int64
func (c *Ctx) Float64(col string) float64
func (c *Ctx) String(col string) string
func (c *Ctx) Time(col string) time.Time
func (c *Ctx) IsNull(col string) bool

type GenFunc func(*Ctx) any

// 供 registry_gen.go 调用
func Register(column string, fn GenFunc)
func Lookup(column string) (GenFunc, bool)
```

**Registry 内部**：进程内 `map[string]GenFunc`，`init()` 中通过 `Register` 填入，`Lookup` 被生成器主循环调用（§8）。重复注册同一列 → `panic`。

### 6.2 返回值类型对照表

| SQL 类型                           | 用户返回 Go 类型            |
| ---------------------------------- | --------------------------- |
| TINYINT / SMALLINT / MEDIUMINT / INT | `int32`                     |
| BIGINT                             | `int64`                     |
| FLOAT / DOUBLE                     | `float64`                   |
| CHAR / VARCHAR / TEXT / BLOB / VARBINARY | `string`              |
| TIMESTAMP / DATETIME / DATE / TIME | `time.Time`                 |
| 任意                               | `nil` → NULL                |

说明：用户统一以 `time.Time` 返回时间类；gen 框架在 parquet 路径内部转 `int64 μs` / `int32 days`，CSV 路径内部按现有 format 规则序列化。用户侧对输出格式差异无感。

返回类型和列 SQL 类型不匹配 → 运行时 panic（被 worker 捕获写进 `tasks.error`）。

### 6.3 列 → 函数名规则

- **PascalCase 映射**：`user_id` → `UserId`，`device_finger` → `DeviceFinger`，`billtime` → `Billtime`。
- 列没有对应的 exported 函数 → 走现有 `ColumnSpec.generate*` 内建路径（§8）。
- 函数存在但签名不符（不是 `func Xxx(*gen.Ctx) any`） → codegen 跳过不注册，运行时视为"无用户代码"走内建路径。

## 7. EC2 launcher 流程 + `cmd/codegen`

### 7.1 `cmd/codegen`（新建，~80 行）

扫描输入目录所有 `*.go` 文件，AST 检测形如 `func Xxx(ctx *gen.Ctx) any` 的 exported 顶级函数，产出 `registry_gen.go`：

```go
// Code generated. DO NOT EDIT.
package user

import "dataWriter/src/gen"

func init() {
    gen.Register("user_id", UserId)
    gen.Register("device_finger", DeviceFinger)
}
```

- 输入参数：`-in <dir> -out <path>`
- 列名从函数名反推：`UserId` → `user_id`（PascalCase → snake_case，下划线前插小写化）。
- 签名不符的忽略，不报错（允许用户写 helper）。
- 同列重复注册 → 让 `gen.Register` 在运行时 panic，codegen 不做去重。

### 7.2 AMI 约定

EC2 AMI 预装：
- Go toolchain（版本对齐 `go.mod`）
- data-writer 源码（默认路径 `/opt/data-writer`）
- `GOCACHE` 持久化到镜像层，让冷启动 `go build` 从 30s 降到 2–5s
- 基线 `bin/data-writer` 二进制（无 user code 版本）

### 7.3 launcher 脚本

EC2 boot 后执行（systemd unit 或 cloud-init 调用）：

```bash
#!/bin/bash
set -e
cd /opt/data-writer

# 1. Claim: 打印 "tid shard total" 或 "0"
read task_id shard shard_total < <(./bin/data-writer -claim-task -dsn "$DSN")
if [ "$task_id" = "0" ]; then
  shutdown now; exit
fi

# 2. Dump generators_go 字段（空则打印空串）
./bin/data-writer -dump-generators -dsn "$DSN" -task-id "$task_id" > src/user/user_gens.go.new

# 3. 若非空：codegen + rebuild
if [ -s src/user/user_gens.go.new ]; then
  mv src/user/user_gens.go.new src/user/user_gens.go
  if ! go run ./cmd/codegen -in ./src/user -out ./src/user/registry_gen.go 2> /tmp/build.err; then
    ./bin/data-writer -report-failure -dsn "$DSN" -task-id "$task_id" -err-file /tmp/build.err
    shutdown now; exit
  fi
  if ! go build -o ./bin/data-writer ./src 2> /tmp/build.err; then
    ./bin/data-writer -report-failure -dsn "$DSN" -task-id "$task_id" -err-file /tmp/build.err
    shutdown now; exit
  fi
else
  rm -f src/user/user_gens.go.new
fi

# 4. Run shard
./bin/data-writer -worker-mode -dsn "$DSN" -task-id "$task_id" \
  -shard "$shard" -shard-total "$shard_total"

shutdown now
```

### 7.4 新增 CLI 子命令（~80 行合计）

- **`-dump-generators -dsn -task-id`**：`SELECT generators_go FROM tasks WHERE id=$1` → 写 stdout。空值打印空字符串，退出码 0。
- **`-report-failure -dsn -task-id -err-file`**：读 err-file 前 64 KB → `UPDATE tasks SET state='failed', error=$content WHERE id=$1`。退出码 0。

`-claim-task` 和 `-worker-mode` 现有，不改。

### 7.5 Shard 并行与重复 build

同一 task 的多个 shard 会在多个 EC2 上分别执行 §7.3 第 3 步的 rebuild——重复做 N 次相同 build。自用最多 8 shard，每次 2–5s，**先不优化**。未来可以让 shard 0 完成后把 binary 推 S3，其他 shard 下载；不在本 spec。

## 8. 生成器主循环接入点

### 8.1 `generate()` 顶部加 `gen.Lookup`

现有 `src/spec/data_gen.go::generate()` (line 169-193) 按 SQL 类型 dispatch。改动：

```go
func (c *ColumnSpec) generate(rowID int, rng *rand.Rand, ctxBuf *gen.RowBuffer) (any, int16) {
    if fn, ok := gen.Lookup(c.Name); ok {
        ctx := gen.NewCtx(rowID, rng, ctxBuf)   // ctxBuf 承载当前行已生成列
        v := fn(ctx)
        if v == nil { return "\\N", 0 }
        return normalizeUserValue(v, c.SQLType), 1
    }

    if c.generateNULL(rng) { return "\\N", 0 }
    // ... 原有 switch（未改）
}
```

`normalizeUserValue`：将 `time.Time` 根据 SQL 类型和输出格式规约到 CSV 字符串，对 parquet 路径另走 §8.3。类型不匹配 → panic。

### 8.2 CSV 路径（行主序）

现有 CSV 已是行主序：每行按 schema 顺序调 `generate()`，把返回值放到 `[]any` 拼行。接入点改动后，`ctxBuf` 在循环外初始化，每列生成完后把值记入 `ctxBuf`，给后续同行列的 `ctx.Int64(...)` 查询用。

改动量：`src/generator/csv_generator.go` + `generate()` 签名扩一个参数。

### 8.3 Parquet 路径（按 row group 切行主序）

Parquet 现在是**列主序 batch**：每列跑完整 row group 才走下一列。此结构无法在列 B 生成时读列 A 的"当前行"值（因为列 A 整个 row group 已经跑完、buffer 都是成品）。

改造：**row group 开始时判断是否有任何列在 `gen.Lookup` 命中**。
- **否**（纯内建路径）：保持现有列主序 batch 逻辑，零改动。
- **是**：此 row group 切换为**按行生成 + 列主序 flush**：
  1. 预分配 N 列 × `rowsPerRowGroup` 的类型化 buffer。
  2. 按 schema 顺序，内层循环行、外层循环列，把每行每列写到对应 buffer 位置。每列生成时 `ctxBuf` 有本行前面列的值。
  3. 一个 row group 全部行生成完 → 按 schema 顺序 `WriteBatch` 到 parquet `SerialRowGroupWriter`。

**内存代价**：row group 内全部类型化 buffer 同时活在堆上。单列大小 ≈ `rowsPerRG × sizeof(elem)`，其中 int32/date = 4B，int64/timestamp/double = 8B，string 约 24B 指针 + 内容字节（典型 20B 字符串 ~44B/entry），再加每列 2B 的 def level。估算：

| `rowsPerRG` | 42 列、均值 ~20 B/entry 的表估算峰值 |
| ----------- | ------------------------------------ |
| 10 K        | ~10 MB                               |
| 100 K       | ~100 MB                              |
| 1 M         | ~800 MB                              |
| 10 M        | ~8 GB（超 16 GB EC2 上限）            |

结论：有用户代码时 `rowsPerRG`（= `common.rows / parquet.row_groups`）应控制在 ≤ 1 M；更大的 row group 会 OOM。dispatch 校验时检一下：若 `generators_go` 非空 且 `rows / row_groups > 2_000_000`，返回 400 让用户调大 `row_groups`。无用户代码的任务不受此约束。

**首次路径探测**：task 启动时扫所有列 `gen.Lookup`，缓存一个 `hasUserCode bool`，row group 循环里查这个缓存即可。

## 9. 错误处理 / 失败语义

| 错误                                          | 报在哪           | 回到哪                                 |
| --------------------------------------------- | ---------------- | -------------------------------------- |
| `/api/scaffold`：SQL 解析失败                  | dispatch         | 400 + message                          |
| `/api/create`：SQL 解析失败                     | dispatch         | 400 + message                          |
| `/api/create`：`generators_go` parse 失败       | dispatch         | 400 + `go/parser` error                |
| `/api/create`：`generators_go` 非空但 `target != ec2` | dispatch   | 400                                    |
| `/api/create`：`generators_go` 非空且 `rows / row_groups > 2M` | dispatch | 400（见 §8.3 内存上限）      |
| EC2：codegen 失败                              | launcher         | `tasks.state=failed`, `error=stderr`   |
| EC2：`go build` 失败                            | launcher         | `tasks.state=failed`, `error=stderr`   |
| EC2：`data-writer -worker-mode` panic          | worker main      | `tasks.state=failed`, `error=panic msg`|
| 运行时：用户函数读未生成列 / 后写列            | `ctx.Int64` 等   | panic → worker 捕获                     |
| 运行时：返回值类型与 SQL 类型不匹配            | `normalizeUserValue` | panic → worker 捕获                 |
| 运行时：重复 `Register`                         | `init()`         | panic → worker 捕获                     |

**不做**：auto-retry、rollback、"降级到默认 generator"。出错即失败，用户改代码重新提交。

## 10. 向后兼容

- 现有 task 行没有 `generators_go` 列值 → SELECT 出 NULL → 走纯内建路径，零回归。
- 所有现有 SQL COMMENT 旋钮（`null_percent` / `max_length` / `mean` / ... ）**不动**，行为不变。
- Web UI 对老任务的渲染不动，新增"Go generators"面板仅在用户显式展开时出现。

## 11. 前端改动 (Web UI)

- **Monaco editor** 组件引入（~2 MB JS，仅 Go 编辑页面按需加载）。
- 现有任务提交页加一个可折叠 "Custom generators (Go)" 区块：

## 13. 对比旧 spec 的精简

相对 `docs/superpowers/specs/column-generation.md`（v0），砍掉了：

| 旧 spec 内容                               | 处理        | 理由                                            |
| ------------------------------------------ | ----------- | ----------------------------------------------- |
| Layer 1 TOML DSL (表达式语言 / stdlib)     | **删**      | 自用 + 新写为主，写 Go 和写 DSL 成本差不多       |
| 表达式解析器 (~400–500 行)                 | **删**      | 随 DSL 一起                                     |
| 拓扑排序 / `col.X` 依赖 DAG                | **删**      | 改成"只能读前列"规则                            |
| Parquet 整-RG buffer 慢路径                | **简化**    | 改成 row group 粒度切行主序（§8.3），更直观       |
| `@go` kind 标记、`deps` 显式声明            | **删**      | 函数名存在 = 注册                               |
| `data-writer scaffold` CLI                  | **移到 Web**| `/api/scaffold` 端点                            |
| import 白名单校验                          | **删**      | 自用信任                                         |
| AST 自动推断 deps                          | **删**      | 无拓扑                                           |
| scaffold 幂等合并                          | **删**      | Web 场景一次生成                                 |
| 服务器 `go build` workspace + 10 行预览    | **删**      | Build 全部放 EC2                                 |
| 任务包文件树（`generators/*.go` 多文件）   | **单文件**  | 整个文件作为一个 DB TEXT 字段                     |

净效果：spec 从 ~550 行收缩到本文档，核心改动集中在 `src/gen` 包 + `generate()` 接入点 + EC2 launcher 脚本 + Web UI 面板。
